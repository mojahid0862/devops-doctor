# DevOps Team

Read [the shared evidence contract](../devops-doctor/references/evidence-contract.md). This skill coordinates native agents available in the current host; installing it does not add an agent runtime or grant permissions.

The main agent applies assess → map → dispatch → reassess → validate/combine. Assigned workers execute their scoped task and return evidence; they do not repeat team planning or load coordinator skills unless assigned coordination. Use a task-appropriate map: a shared MR diff, failed-job evidence, billing/utilization evidence, or disjoint implementation scopes. A single service or incident may still have useful independent questions. Keep tiny tasks direct and actual dependencies ordered; do not invent unrelated work to fill slots.

For broad requests such as "check backend health" or "check all backend services," follow [the backend health workflow](references/backend-health.md). Default to native delegation when two or more useful independent check groups and worker slots exist; do not wait for the user to mention agents. The main agent builds one shallow resource map, dispatches known groups as soon as their inputs are ready, and expands or reuses the team as remaining work becomes clear. Do not finish a serial health sweep before deciding whether to delegate.

## Select a team

For a continuation or repeated task, first compare the previous canonical coverage with the current scope, source revisions and mutable-state freshness. Reuse compatible workers and verified unchanged analysis; refresh changed, uncertain or stale evidence and run requested checks. Do not automatically restart an independent full review of unchanged source. A requested independent audit still needs independent analysis. Label an unchanged-source recheck clearly, and compare it separately from a fresh investigation in performance reports.

1. One main agent coordinates up to 20 concurrent subagents for a task; 20 is a ceiling, not a target. Count all concurrent descendants together, excluding the main agent; this is not a separate allowance of 20 for each worker. Use current native capacity, accounting for occupied slots and the main agent when the host limit includes it. A configured ceiling or a previous run's worker count does not prove current availability.
2. Use available native create/spawn, message, wait, and interrupt tools. Check their current schemas and runtime limits. Do not launch nested Codex processes, make API calls to create agents, or create user-owned chats as substitutes. If delegation is unavailable, state that and perform the same scoped checks sequentially; if the user requires independent agents, report that capability gap.
3. Quickly partition substantial work by independently executable module, service/resource, job, region, or question. Batch trivial or tightly coupled work before counting. A broad role or category containing many ready independent investigations must not become one oversized assignment merely to minimize worker count. Set initial worker width to the minimum of ready nontrivial packages, free native worker slots, the remaining concurrent 20-descendant budget, and any explicit task concurrency limit. Apply real access, rate, or hard budget constraints; a general token-saving preference calls for narrow context and evidence reuse, not serializing substantial ready work. Small or strictly dependent tasks stay direct.
4. Select only relevant [specialist roles and team patterns](references/roles.md); repeat roles for distinct scopes without treating the templates as a cap. Briefly state the initial count and its work/capacity basis, separately from the maximum. If substantial work has only one or two ready branches, explain the actual dependency or constraint rather than inventing more work. The main agent owns sizing, expansion, reuse, reassignment, and reduction within authorization and limits, without routine approval prompts. Do not load all specialist skills. Inherit the current model unless the user or applicable instructions request otherwise.

## Delegate with boundaries

- Give each worker one question, task ID, exact scope, success condition, and the minimum necessary sanitized context. Include existing user constraints and authorization explicitly, especially when using an isolated context.
- Minimize delegated context. For a self-contained assignment, prefer the host's isolated-context spawn mode (such as `fork_turns: "none"`) and provide relevant file/evidence references plus essential instructions. Inherit broader history only when the worker needs it. Ask for concise findings, evidence locations, blockers, and actual validation; allow extra detail when needed for correctness. Keep the selected model unless the user or applicable instructions request a change; lower price is not the same as fewer tokens.
- Pin evidence to account/region/resource/time window, GitLab host/project/head SHA, or a Terraform plan content hash. Reuse exact-revision local source or collector results whose identity, completeness and freshness satisfy the question. Verify Git repository identity and required commit/objects; read those objects or matching worktree files. Refresh affected evidence when context changes and mutable head/deployment/auth state when needed, not every source file solely for provenance. Unverified identity remains provisional or blocked. See [reuse gates](../devops-doctor/references/investigation-efficiency.md#evidence-reuse-and-bounded-reads).
- For large or batched source reads, index symbols/routes/fields with `rg -n` or revision-pinned `git grep -n`, then use [source_slice.py](../../scripts/source_slice.py) with the [absolute invocation and coverage rules](../devops-doctor/references/investigation-efficiency.md#pinned-source-reader). Read complete relevant functions, guards and callers in disjoint windows; share filename/revision/read-range pointers to avoid rereads. Compare copied source by immutable blob hash; analyze identical bytes once for the same question while checking distinct wiring/config.
- Assign one owner to each remote collection and each writable path. Reviewers reuse immutable saved evidence. Two writers must never own the same file or overlapping directories at once. Shared workspaces are not isolated worktrees.
- Default workers to investigation/review only. A worker may make authorized reversible local edits solely within assigned paths. Root retains production mutation, merge/push, and external-message execution within existing user authorization; delegation never expands permission.
- Order only actual dependencies. Run independent investigators together. Once a patch is frozen, tests and independent review may overlap when they do not change shared inputs; use separate temporary outputs and invalidate affected results after edits. A reviewer may assess partial evidence to reject an unsupported claim; blocked required tasks still prevent a complete aggregate.
- Workers must not spawn descendants unless the coordinator delegates a specific child task within the same total budget. A blocked worker returns its blocker; it must not switch credentials, broaden scope, or retry indefinitely.

Use [the plan/report contract](references/handoffs.md) and `agent_handoff.py` when a durable or resumable handoff would help; team size alone does not require JSON artifacts. Choose one canonical worker result: a compact message/table or a required report file, with evidence pointers. Do not repeat its content across narrative reports, evidence indexes, provenance files or formatting code without a required consumer or distinct verification need. Keep necessary bulk evidence separately and reference it.

Keep a minimal participation roster for the current task from native tool receipts, execution status, and returned work. Check status by known worker IDs or the current task prefix, requesting metadata-only results where supported. Use current host-declared capacity and known occupied slots; request minimal global capacity metadata only when free capacity cannot otherwise be established or has changed. Do not load unrelated historical final summaries or findings just to check active workers. Record each actual worker identity, its assignment, and outcome; include descendants. Count a worker once when its execution is confirmed, even if reused for several assignments. Exclude historical agents unrelated to this task, planned roles, failed spawn attempts, and simulated workers. A successful dispatch with no confirmed execution is still unverified. If a count cannot be established, say so rather than infer it from plan width or report count.

## Reassess team size during the task

- Reassess after a worker result, newly discovered work, a blocker, or a material delay reported by a worker or observed during a bounded wait. Track ready, running, blocked, and completed tasks, their dependencies, and the current worker count. Do not wait for all workers to finish before reassessing.
- Fill free capacity from ready nontrivial packages using the sizing rule above; do not hold ready work behind an unrelated slow branch. Reuse compatible idle workers when their retained context helps; otherwise use a concise fresh handoff. Revisit large remaining assignments and stragglers for independently executable parts, especially after new scope appears. Avoid creating work solely to fill slots.
- Distinguish an oversized assignment from an external wait. A pending job, missing credentials, an API rate limit, or an unresolved prerequisite will not be fixed by duplicate workers. Keep those branches blocked or waiting while dispatching other ready work.
- Before splitting an in-progress assignment, coordinate with its owner. Make the retained and delegated scopes explicit; stop or obtain acknowledgment of relinquished ownership before another worker takes those paths or reads. Update the task plan and handoffs, preserve completed evidence, and invalidate only conclusions affected by changed scope or evidence.
- Shrink the team as ready work decreases; reuse or release idle workers using the host's supported lifecycle. If the host counts open workers, idle or interrupted workers may still occupy slots; check availability before spawning replacements. Never leave duplicate or obsolete work running. Briefly report a meaningful size change and why, such as "Expanding from 3 to 5 workers for two newly found independent services." More workers are justified by useful parallel work, not elapsed time alone.

## Coordinate and finish

1. Before deep main-agent investigation or any wait, dispatch useful ready branches within capacity. Then work on a distinct part while agents run. Dispatch newly ready work as slots become available without waiting for unrelated slow branches or a planning batch. Prioritize tasks that unblock downstream work; require only that branch's own inputs. Reuse compatible idle workers and share critical discoveries promptly.
2. Use bounded waits and meaningful progress updates. Before waiting, check that all useful ready branches have been dispatched within capacity. For performance evaluations, verify overlapping execution from native start/end receipts and measure coordinator plus worker tokens when available; dispatch counts alone do not prove parallelism. Silence or elapsed time is not completion. On cancellation, scope change, duplicate work, or an exhausted user budget, interrupt affected workers and collect their partial findings.
3. Each worker's canonical result contains findings and relevant negative findings, source references, revision/observed time, confidence, blockers, changed paths, and tests actually run. Follow-ups return only new or changed facts and evidence pointers. Preserve exact technical details and missing/partial evidence; do not turn proposed commands into completed checks.
4. Reconcile conflicting facts against source/time/scope. Do not resolve contradictions by majority vote. Ask for a narrow verification or report the disagreement as unresolved.
5. Assign independent review when security/production risk, complexity, or uncertainty justifies it; file count alone is not a trigger. Give the reviewer raw evidence or the immutable patch, not prior conclusions as an answer key. Review may overlap independent validation; repeat a query only for freshness, missing coverage or a discrepancy. Reuse existing safe tests/harnesses after checking source compatibility, assertions and isolation; independent conclusions do not require recreating test infrastructure.
6. The coordinator inspects decisive evidence, integrates permitted changes, runs the smallest relevant final checks, and produces one answer by referencing or merging canonical results. Do not rewrite every worker's detail into another schema, checklist or generated report without a required deliverable or distinct verification need. Never declare deployment, merge, or remediation complete from agent consensus or the handoff validator's exit code.

Conclude with the result, decisive evidence, remaining gaps, and `Changed | Validate | Next`. Always include `Agents used: 1 main + N subagents = T total` for the current task, with N distinct confirmed participants and T = N + 1. Use zero subagents when the main agent worked alone. This is the number used across the task, not a claim that all ran simultaneously; optionally show verified peak concurrency separately. Disclose failed, cancelled, or partial worker outcomes when present, so the count does not imply every worker completed successfully. Name delegated roles briefly when useful, without dumping worker IDs or inter-agent transcripts or implying continued monitoring.
