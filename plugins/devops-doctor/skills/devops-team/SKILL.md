# DevOps Team

Read [the shared evidence contract](../devops-doctor/references/evidence-contract.md). This skill coordinates native agents available in the current host; installing it does not add an agent runtime or grant permissions.

For broad requests such as "check backend health" or "check all backend services," follow [the backend health workflow](references/backend-health.md). Default to native delegation when two or more useful independent check groups and worker slots exist; do not wait for the user to mention agents. The main agent builds one shallow resource map, dispatches known groups as soon as their inputs are ready, and expands or reuses the team as remaining work becomes clear. Do not finish a serial health sweep before deciding whether to delegate.

## Select a team

1. One main agent coordinates up to 20 concurrent subagents for a task. Choose how many are useful from independently answerable questions, ready work, the user's budget, and actual host capacity; 20 is a ceiling, not a target. Tiny tasks stay direct. Count all concurrent descendants together toward 20, excluding the main agent; this is not a separate allowance of 20 for each worker. A configured ceiling does not prove that slots exist: apply any lower host or user limit and report it clearly.
2. Use available native create/spawn, message, wait, and interrupt tools. Check their current schemas and runtime limits. Do not launch nested Codex processes, make API calls to create agents, or create user-owned chats as substitutes. If delegation is unavailable, state that and perform the same scoped checks sequentially; if the user requires independent agents, report that capability gap.
3. Select only relevant [specialist roles and team patterns](references/roles.md). Multiple workers may use the same role for distinct scopes; six templates do not limit worker count. Estimate the initial team from ready independent work and state that count with a brief reason, separately from the maximum allowed budget. The main agent owns initial sizing, expansion, reuse, reassignment, and reduction; do not ask the user to choose or approve these routine decisions within the authorized task and limits. The starting count can change during the task. Do not load all specialist skills. Inherit the current model unless the user or applicable instructions request otherwise.

## Delegate with boundaries

- Give each worker one question, task ID, exact scope, success condition, and the minimum necessary sanitized context. Include existing user constraints and authorization explicitly, especially when using an isolated context.
- Minimize delegated context. For a self-contained assignment, prefer the host's isolated-context spawn mode (such as `fork_turns: "none"`) and provide relevant file/evidence references plus essential instructions. Inherit broader history only when the worker needs it. Ask for concise findings, evidence locations, blockers, and actual validation; allow extra detail when needed for correctness. Keep the selected model unless the user or applicable instructions request a change; lower price is not the same as fewer tokens.
- Pin evidence to account/region/resource/time window, GitLab host/project/head SHA, or a Terraform plan content hash. A context change invalidates dependent conclusions; mark affected work stale and refresh only what is necessary.
- Assign one owner to each remote collection and each writable path. Reviewers reuse immutable saved evidence. Two writers must never own the same file or overlapping directories at once. Shared workspaces are not isolated worktrees.
- Default workers to investigation/review only. A worker may make authorized reversible local edits solely within assigned paths. Root retains production mutation, merge/push, and external-message execution within existing user authorization; delegation never expands permission.
- Resolve dependencies before dispatch. Run independent investigators together; run fix, then tests, then independent review in order when they share artifacts. Freeze a patch/evidence version for review. A reviewer may assess available partial evidence to reject an unsupported claim; blocked required tasks still prevent a complete aggregate.
- Workers must not spawn descendants unless the coordinator delegates a specific child task within the same total budget. A blocked worker returns its blocker; it must not switch credentials, broaden scope, or retry indefinitely.

For complex or resumable teams, use [the plan/report contract](references/handoffs.md) and `agent_handoff.py` to check ownership, dependencies, coverage, and contradictions. For a small two-task read-only split, the same fields can be conveyed in concise messages without writing JSON.

Keep a minimal participation roster for the current task from native tool receipts, execution status, and returned work. Record each actual worker identity, its assignment, and outcome; include descendants. Count a worker once when its execution is confirmed, even if reused for several assignments. Exclude historical agents unrelated to this task, planned roles, failed spawn attempts, and simulated workers. A successful dispatch with no confirmed execution is still unverified. If a count cannot be established, say so rather than infer it from plan width or report count.

## Reassess team size during the task

- Reassess after a worker result, newly discovered work, a blocker, or a material delay reported by a worker or observed during a bounded wait. Track ready, running, blocked, and completed tasks, their dependencies, and the current worker count. Do not wait for all workers to finish before reassessing.
- Add workers when independent work or review offers enough speed or quality benefit to justify additional context and reporting tokens. Split large assignments only when the parts can progress independently. Reuse compatible idle workers first, then spawn additional workers as useful, up to the shared 20-worker ceiling and any lower user/runtime limit. Make this adjustment autonomously within the existing scope, authorization, and budget; the user need not manually request each increase. Twenty available slots are not a reason to use twenty workers.
- Investigate why work is slow before increasing concurrency. A pending external job, missing credentials, an API rate limit, or an unresolved prerequisite will not be fixed by duplicate workers. Keep those branches blocked or waiting, and delegate other ready work if available.
- Before splitting an in-progress assignment, coordinate with its owner. Make the retained and delegated scopes explicit; stop or obtain acknowledgment of relinquished ownership before another worker takes those paths or reads. Update the task plan and handoffs, preserve completed evidence, and invalidate only conclusions affected by changed scope or evidence.
- Shrink the team as ready work decreases; reuse or release idle workers using the host's supported lifecycle. If the host counts open workers, idle or interrupted workers may still occupy slots; check availability before spawning replacements. Never leave duplicate or obsolete work running. Briefly report a meaningful size change and why, such as "Expanding from 3 to 5 workers for two newly found independent services." More workers are justified by useful parallel work, not elapsed time alone.

## Coordinate and finish

1. Work on a distinct part while agents run. Dispatch a ready task as soon as a slot becomes available; do not wait for unrelated slow tasks or an entire planning batch. Prioritize tasks that unblock downstream work, and only dispatch dependent work once its own required inputs are adequate. Reuse an idle worker for related follow-up when its context is still valid. Share a changed scope or critical discovery promptly.
2. Use bounded waits and meaningful progress updates. Silence or elapsed time is not completion. On cancellation, scope change, duplicate work, or an exhausted user budget, interrupt affected workers and collect their partial findings.
3. Each worker returns findings with source references, observed time, confidence, unresolved blockers, changed paths, and tests actually run. Report missing evidence explicitly; do not turn proposed commands into completed checks.
4. Reconcile conflicting facts against source/time/scope. Do not resolve contradictions by majority vote. Ask for a narrow verification or report the disagreement as unresolved.
5. For a material security finding, production-impact proposal, or multi-file change, assign an independent reviewer after the relevant evidence/patch is ready. A reviewer gets the scope and evidence without being coached toward the author's preferred verdict. Review only needs to repeat a query when freshness or a discrepancy requires it.
6. The coordinator inspects decisive evidence, integrates permitted changes, runs the smallest relevant final checks, and produces one answer. Never declare deployment, merge, or remediation complete from agent consensus or the handoff validator's exit code.

Conclude with the result, decisive evidence, remaining gaps, and `Changed | Validate | Next`. Always include `Agents used: 1 main + N subagents = T total` for the current task, with N distinct confirmed participants and T = N + 1. Use zero subagents when the main agent worked alone. This is the number used across the task, not a claim that all ran simultaneously; optionally show verified peak concurrency separately. Disclose failed, cancelled, or partial worker outcomes when present, so the count does not imply every worker completed successfully. Name delegated roles briefly when useful, without dumping worker IDs or inter-agent transcripts or implying continued monitoring.
